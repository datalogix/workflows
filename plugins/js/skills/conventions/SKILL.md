# Datalogix conventions for JavaScript and TypeScript

These rules add to `core:conventions`, which has the language, scope, validation limits, review rounds and pull request rules: load both.

## Feature flags and phased rollout

In projects that already use a feature flag library or service (for example `flags` from Vercel, `@vercel/flags`, LaunchDarkly, Unleash, GrowthBook, PostHog or their own module), new user-facing behavior ships behind a flag, unless the issue says otherwise:

- Define the flag the way the project already defines its flags, enabled only for internal users first. Reuse the project's existing way of identifying team members or admins; if there is none, enable it for nobody and say so in the PR.
- Keep the old behavior working while the flag is off. Removing the flag and the old code path is a separate, later PR.
- Rollout stages are separate PRs that only change who gets the flag: internal users, then a share of users, then everyone.
- Mention the flag and its current stage in **Observações**.

Projects without a flag library ship without one: do not add a library for it.

## Database migrations

Every deploy can be rolled back by redeploying the previous commit, which does not undo migrations (Prisma, Drizzle, Knex, TypeORM and the like). Migrations must therefore keep the previous release working:

- Only additive changes (new tables, new nullable or defaulted columns, new indexes) in the same PR as the code that uses them.
- Never drop or rename a column or table that the previous release still uses, and never change a column's type in place. Do it in steps across separate PRs: add the new structure, move the code to it, and remove the old structure only after that release is stable.
- Never edit a migration that is already on the default branch.

## Tests

- Create or update automated tests **only** if the project already has real tests (a test runner such as Vitest, Jest, Playwright or Cypress configured, with test files beyond an example generated by a starter).
- If the project has no tests, do not create them.

## Validation

- Use the project's scripts to learn how it runs its tools: read `scripts` in `package.json` (`typecheck`, `lint`, `test`, `test:e2e`, `build`) and use the same package manager and options, filtered to your change (e.g. `npm run test -- <file>`, `pnpm vitest run <file>`, `npx eslint <files>`).
- The package manager is the one of the lockfile: `pnpm-lock.yaml` (pnpm), `yarn.lock` (Yarn) or `package-lock.json` (npm). Never add another lockfile.
- Run the end-to-end tests (`test:e2e`) only for the specs related to your change, when the project has them.

## Pre-PR verification

The checks to run on what you changed (see `core:conventions`; never loosen `tsconfig.json`, add `@ts-ignore`, `eslint-disable` or `.skip` to pass):

1. The `typecheck` script of `package.json` (or `npx tsc --noEmit` in a TypeScript project without one).
2. The `lint` script, or the linter on the changed files.
3. The tests related to the change, through the `test` script, and the related `test:e2e` specs when the project has them.
4. The `build` script, when you changed routes, server code, configuration or dependencies: Next and Nuxt report rendering and route errors only there.
5. The audit of the lockfile you changed (`npm audit --audit-level=high`, `pnpm audit --audit-level high`, `yarn audit --level high` or `yarn npm audit --recursive --severity high`).
