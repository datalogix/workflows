# Troubleshooting

| Problem                                    | Check                                                                                                                                        |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude does not react to `@claude`         | The author has write access to the repository (a notice in the run says otherwise); the Claude GitHub App is installed; `CLAUDE_CODE_OAUTH_TOKEN` is available to the repository. A request made while Claude is already working on the same issue or pull request waits; if another one arrives meanwhile, the waiting one is dropped (GitHub keeps one pending run per issue): ask again after the run ends |
| The security review fails on a pull request that changes `.github/workflows/datalogix.yml` | Expected: Claude only runs with the default branch's copy of the workflow file, and the comment says so. Move the workflow change to a pull request of its own (an admin merges it past the check), then push to the first pull request or re-run its job |
| Claude jobs fail asking for the token      | On GitHub Free, organization secrets do not reach private repositories: set `CLAUDE_CODE_OAUTH_TOKEN` as a repository secret ([Organization setup, step 2](organization-setup.md#2-generate-the-claude-token)) |
| An issue form does not start Claude        | The `claude` or `claude-plan` label exists in the repository (run `check`)                                                                   |
| `setup` says the repository was not found  | Run `gh auth status`: the login must see the repository (`gh auth login`, or `gh auth refresh` for organization access)                      |
| `setup` or `check` stops with "Cannot read the … of OWNER/REPO" | The named read failed (permission or network): run `gh auth status`, check that your login can manage that repository's settings, and run it again |
| `setup` cannot register the relay          | Run `npx wrangler login`, and check that `org` deployed the relay (`workflows/relay.json` in the organization's `.github` repository). On Windows setup skips this step: store the secret by hand ([Manual setup](laravel/app-manual-setup.md#relay)) |
| `claude-fix-ci` never runs                 | `fix-ci` is on; the `tests` job failed on a pull request (not on a push or in the merge queue); the branch starts with `claude/` and is not from a fork; it has fewer than 2 `[ci-fix]` commits (after that Claude comments once asking for human review); no newer commit was pushed after the failed one |
| Wrong PHP version                          | Add a `.php-version` file or pass `php-version`                                                                                              |
| `composer install` fails on a private package | Not supported: the workflows pass no Composer credentials (`COMPOSER_AUTH`), so only public packages can be installed |
| Views fail with "Vite manifest not found"  | Check the warning of the _Build frontend assets_ step in `setup-laravel`                                                                     |
| Pint fails with an unknown `--diff` option | Update `laravel/pint` to 1.20+, or turn it off with `pint: false` (setup: uncheck Laravel Pint)                    |
| A pull request waits for a check forever   | The required check name matches `<calling job> / <job> / <job>` (e.g. `pipeline / tests / tests`), and the calling workflow has no `paths` filter and has the `merge_group` trigger; the layer of that check is on (`check` reports a required check whose layer is off) |
| `risk-gate` fails after an approval        | The approval was given on an older commit with other changes (a push that changed the diff, a merge or rebase that moved the pull request's lines, or changes GitHub cannot compare): approve the current commit. Or the approver has no write access to the repository |
| `release` fails with "Cannot compare … check that both branches exist" | The default branch and the `production-branch` both exist on GitHub: `check` reports a missing production branch, and setup creates the missing one |
| A deploy fails at _Check configuration_    | The environment is named exactly `staging` or `production` and has the `DEPLOY_HOOK` secret and the `HEALTH_URL` variable                    |
| Every deploy is rolled back                | `HEALTH_URL` answers `200` from outside (no basic auth or IP restriction on it); the wait is long enough: `project` waits 120 s on Forge and 300 s on Laravel Cloud before watching (`settle-seconds` changes it) |
| `setup` says the Forge or Laravel Cloud API token cannot do something | The Forge token has the `site:manage-deploys` permission and belongs to an organization with the site; the Cloud token belongs to the organization of the application. Without a token, setup lists those settings to change by hand |
| `setup` finds no Forge site or Cloud environment of the repository | The site (or application) is connected to this GitHub repository: setup compares its repository with `owner/repo` |
| A Forge rollback deployed the latest code  | The deploy script checks out `FORGE_VAR_COMMIT` ([step 2](laravel/app.md#step-2-do-what-setup-cannot))                                                     |
| Monitoring problems do not open issues     | The worker logs show `204` (otherwise see [what each status means](../relay/README.md#troubleshooting)); the project workflow has the `repository_dispatch` trigger; the environment is listed in `incident-environments` |
| An issue shows no release information      | The monitoring environment has the same name as the GitHub environment (`production`, `staging`), in any letter case, and `project` has deployed to it at least once |
| The `rollback` label does nothing          | `project` has `deploy` set; the person who added the label has write access; a release before the live one was recorded by `project`; the issue has the `env:staging` or `env:production` label. A rollback waiting for another deploy is dropped if a newer run arrives (GitHub keeps one pending run per environment): remove the label and add it again |
